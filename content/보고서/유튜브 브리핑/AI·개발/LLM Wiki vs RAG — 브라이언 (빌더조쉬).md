# 📌 LLM Wiki vs RAG — 브라이언 (빌더조쉬)

- **채널명**: 빌더 조쉬 Builder Josh

> [!abstract] 핵심 요약 (Executive Summary)
> - LLM Wiki는 "문서를 벡터DB에 넣는" RAG가 아니라, 원재료(Raw)를 **ingest 스킬로 분해·연결해 사람이 읽는 마크다운 위키(Wiki)로 색인**하는 방식이며, 성패는 도구가 아니라 **"왜 캡처했는지"를 AI가 나에게 질문하게 만드는 목적·컨텍스트 입력**에서 갈린다.


## 1. 핵심 주장 (그대로)

- "세상에서 가장 가치 있는 것은 내 지식이다." 기록은 **시간여행**이며, 기록을 남기는 행위는 **세이브 포인트 생성**이다. 시간은 가장 희귀하고 가치 있는 자원.
- AI가 좋은 답을 주는 것과 **나를 아는 것**은 다른 문제. 내 기록이 있으면 "왜 이걸 묻는지" 맥락을 이해해 훨씬 직관적인 답이 나온다.
- 관리(management)의 정의를 **검색(retrieval)을 쉽게 하기 위한 정리**로 한정. 다 기록할 필요는 없다 — 필요할 때 꺼낼 수 있으면 충분. 단 **LLM이 읽을 수 있으면 더 좋다**.
- LLM Wiki는 "대단한 발명이 아니다". 그런데도 폭발한 이유는 **두 축이 만났기 때문**:
  1. AI가 눈에 띄게 똑똑해짐
  2. 지식이 AI가 잘 읽는 포맷으로 정리되기 시작
- 그 전(4월 이전)에도 Open-Claude(오역 가능)·Hermes 같은 걸로 "텔레그램에서 24/7 나를 아는 에이전트"를 꿈꿨지만, **그 밑에 깔 지식베이스가 없었다.** 때맞춰 LLM Wiki가 나와 폭발했다(화자 본인의 해석이라고 명시).
- 지식관리의 실패 원인은 두 가지: **목적 미정의**와 **구조화 실패**. 구조화는 "내가 세상을 인식하는 방식"을 시스템으로 갖는 일인데, 그 경험이 없어서 실패한다.
- 언제든 아무 문서나 "ingest 해줘"라고 던지면 안 된다. **가치 있다고 판단한 문서만**, 그리고 **"내가 누구이고 왜/무엇을 위해 넣는지"를 함께** 넣어야 의도대로 정리된다.

## 2. LLM Wiki가 RAG와 다른 점

- **기원**: Andrej Karpathy의 트윗 한 건. 명칭은 "LLM Knowledge Base". 요구사항 4가지 — ① 유튜브·PDF 등 데이터를 **ingest** ② LLM이 소화하기 쉬운 형태로 검색하는 **프론트엔드(당시 Obsidian 언급)** ③ Q&A로 검색해 좋은 아웃풋 생성 ④ **링킹**으로 정리.
- **정의**: "LLM과 함께 편집·접근하는 지식베이스". 나무위키·위키백과 같은 공유 지식베이스의 **LLM 동참 버전**.
- **갱신 비용**: RAG는 새 문서가 들어올 때마다 업데이트/re-index 비용이 든다. LLM Wiki는 **새 문서 추가 시 전체를 재색인할 필요가 없다**(해당 부분만).
- **저장 형태**: RAG는 임베딩·청킹 후 **벡터DB에 바이너리 형태**로 저장 → 사람이 못 읽는다. LLM Wiki는 **마크다운 기반 사람이 읽는 문서**로 저장되고, LLM이 정리해 보여준다 → **인간에게도 더 낫다**.
- **정제 시점**: LLM Wiki는 문서가 **처음부터 entity·concept로 분해·연결**된 상태로 ingest되어 AI 최적 문서가 된다. RAG는 빌드 시 문서가 refine되지 않으면 맥락이 제대로 정리되지 않아 활용 효율이 떨어진다.
- **"연결"이 본질**: 질문자는 ingest를 "마크다운 변환 작업"으로 이해했으나 화자는 **"변환"이 아니라 "연결"**이라고 정정. ingest는 곧 **내 위키의 목차(index)를 만드는 일**이고, 링크를 따라 항해하며 검색한다.
- **적용 범위**: 개인용에만 유리한 게 아니라 **기업 레벨에서도 훨씬 우수**하다고 봄. 문서가 정리되는 순간부터 AI 최적 구조로 들어가기 때문. 단 "어느 쪽이 무조건 낫다고는 말할 수 없다"고 유보.
- **온톨로지**: 화자가 현재 집중하는 키워드. Palantir 온톨로지의 3요소로 **entity / relation(relationship) / object(오역 가능)**를 언급하고, 이 요소들이 위키 안에 통합될 수 있다고 함.
  - **온톨로지 = 질서(일관성을 위한 시스템)**, **지식그래프 = 그것을 내 버전으로 구현한 것**.
  - 예: 커피 온톨로지 = 원두·바리스타. 스타벅스 지식그래프 = 어떤 원두, 어느 직원(= 인스턴스).
  - 온톨로지를 그래프로 그리는 대신 **문서(documentation)로 표현하는 것을 강조** — "결국 문서화가 질서". 지식이 입력된 뒤 어떻게 조직·연결되는지는 그 매뉴얼에 달려 있다.

## 3. 구축·운영 방법 (단계별)

### 3-0. 시작점 — 컨텍스트 먼저, 도구는 나중

1. **기존 기록을 전부 수집**한다(폰·메신저에 흩어진 것 포함).
2. **가장 성능 좋은 모델**로 그 기록을 다 읽히고 → "나는 누구이고 무엇을 가치 있게 여기는가"를 설명하는 **문서 하나로 종합**시킨다.
   - 활용 프레임워크: 이나모리 가즈오(稲盛和夫), 사이먼 시넥(Simon Sinek)의 『Start with Why』. "왜 일하는가"를 과거 기록과 선택에서 추출.
3. 그 문서를 기반으로 **어떤 지식을 모을지, 무엇을 성취할지**를 결정한다.
   - 화자 본인 예: 취미 유튜버로서 영상 제작 / 강의·콘텐츠 제작 / 본업인 AI 전환 컨설턴트로서 교육·컨설팅.
4. 이 **프로필 + 목적**이 위키 안에 상주해야 맥락이 제대로 수집·정리된다. 이것이 "매우 첫 단계".

### 3-1. 볼트를 두 개로 분리

- **Wiki 볼트 ①(깊은 학습용)**: 본질을 추출해 진짜 이해를 위해 남기는 기록.
- **Wiki 볼트 ②(가벼운 소비용)**: 깊게 공부할 필요는 없지만 나중에 참고할 것을 모으는 통상적 LLM 위키.

### 3-2. 수집(캡처) — Raw 폴더로

- **Obsidian Web Clipper**(노션 클리퍼 유사)로 캡처. **용도별 템플릿**을 만들어 둠.
- 유튜브에서 클리퍼를 클릭하면 템플릿이 **자막(transcript) 전체까지** 가져온다 → 볼트의 **`Raw/`** 폴더에 저장.
- 정리는 그때 하지 않고, 나중에 노트 위치를 복사해 **"Ingest this"**로 한 번에 처리.

### 3-3. ingest 스킬 — 남들과 다른 지점

- 폴더는 **`Raw/`(원재료) / `Wiki/`(분해·색인)** 2단. **별도의 ingest 스킬**을 직접 운용.
- ingest가 하는 일: **소스 정리 → entity를 concept으로 분할 → 서로 연결**.
- **차별점**: 남들이 만든 ingest 스킬은 그냥 자동 정리한다. 화자는 ingest가 **나에게 질문하도록** 설계했다.
  - 질문 예: "왜 이 영상을 캡처했나? 어디서 가치를 찾았나? 앞으로 무엇에 쓸 것인가?"
  - **실제 입력 예시(그대로)**: "AX 관련 업무를 하고 있고, 컨설팅 회사가 어떻게 접근하는지 흥미로웠다. 내 생각과 다른 점보다, **'Enterprise IQ'** 개념 — 기술 도입(adoption)이 끝이 아니라 회사가 사업을 어떻게 하는가 — 가 공통적으로 흥미로웠다."
- 이렇게 **목적·관점·향후 용도까지 정제해 입력**하면 → AI가 실시간으로 개념을 인식해 **4~5개 노트로 즉시 분할**한다. "원재료가 아니라 내 생각"이 담긴다. 화자는 이 과정을 **"무의식의 의식화"**라고 부름.
- 효과: 나중에 **BCG가 등장하는 다른 영상**을 캡처하면 자동으로 BCG 노드에 연결된다. (영상에서 BCG는 'AI adoption'이 아니라 **'AI deployment'**라는 용어를 쓴다고 언급.)

### 3-4. 하루 기록 5단계 — Intent → Execution → Reality → Interpretation → AI Log

- **① Intent(의도)** = 데일리 노트의 플래너.
  - 직접 쓰거나 AI와 함께 씀. 아침 이동 중 **Hermes 에이전트**로 폰에서 "내일 계획 세우자"라고 지시.
  - 이미 써둔 게 있으면 **질문을 던져 더블체크**하고, 주간 계획·투두·캘린더를 보고 **추천안을 제시**.
  - 초안 등록 → 사람이 검증·승인. "계획대로 되리란 보장은 없지만, 생각한 계획으로 하루를 보내는 것과 안 그러는 것은 다르다."
- **② Execution(실행)** = 실제로 한 일의 원데이터.
  - **24시간 목걸이형 웨어러블**로 녹음(자막상 기기명 "O" — 오역 가능). 2분간 녹음이 없으면 음성이 잡힐 때 트리거 → **이벤트/메모리로 분리·요약**, **원본 트랜스크립트는 옵시디언에 저장**.
  - **Plaud Note**(사람 만날 때·회의 기록용) 병행.
  - 데일리 노트에 **타임스탬프를 적극 사용**(예: "18:40, 스타벅스 앞, AI 리뷰 했다"). 일부는 손으로 타이핑(불렛저널식), 일부는 자동 누적.
  - **AI와의 대화도 기록 대상**: `log` 스킬이 대화 내용을 요약해 타임스탬프와 함께 남긴다. 프로젝트에도 **`/log`**로 기록 → 새 세션에서 누적 로그를 불러오면 메타데이터가 다 있으므로 **"어디서 끝나고 시작했는지" 노트 한 장만 추가하면 중간 저장점(intermediate save point)** 역할을 한다.
  - 자동 예시: 7월 13일 기록은 AI가 작성 — TED 강연을 보고 **핵심 테이크어웨이를 스스로 식별해 자동 등록**.
  - Execution은 플래너·캘린더 대비 **"계획 대 실제" 대조(reconciliation)** 과정이기도 하다.
- **③ Reality(현실)** = 말로 표현되지 않는 부분까지. 실행과 겹치지만 **컴퓨터 화면을 24시간 녹화**해 커버.
  - **ScreenPipe**(MCP 지원)로 하루 종일 기록 → **MCP를 통해 대화형으로 질의**. 맥북 교체 후 **컴퓨터 오디오도 녹음**.
  - 클릭 로그·연 창 등이 **마크다운으로 변환**되어 "**My Data**"에 라이프로깅처럼 누적(Claude 데이터, Omni 데이터 — 명칭 오역 가능, Screenpipe 데이터).
  - ScreenPipe는 **30분마다 AI가 요약**. 항상 돌아가므로 **로컬 모델**을 쓴다.
  - 즉 "녹화 파일"이 아니라 **녹화 → 마크다운 변환의 반복 프로세스**가 자산이 된다. "모든 순간으로 시간여행이 가능하다."
- **④ Interpretation(해석)** = 회고를 AI가 대신 수행.
  - **매일 새벽 2시에 전체 라이프 데이터 기반 회고 자동 실행**. **어떤 데이터를 썼는지 표시**하고, "오늘의 one thing"을 식별. 데이터 기반 권고·달성 항목 정리.
  - 주기: **일간 → 주간 → 월간 → 분기 → 연간**. 화자는 10년간 기획·회고를 해왔고 매년 연말 **"Life Accounting"** 프로그램을 직접 운영.
  - 핵심 통찰: **기억은 서사(narrative)로 저장된다.** 그래서 분기별로 조각을 모아 "이 해가 어땠는지 **이야기로 만들어 달라**"고 요청 → AI가 **머릿속 연도 서사와 정확히 일치하는 이야기**로 되돌려줌.
- **⑤ AI Log** = 위 과정에서 나온 대화·작업 로그(③·④에서 설명된 `log`/`/log` 스킬 출력이 여기에 해당).

### 3-5. 확장 계획

- 텔레그램에 **에이전트를 분리 운영**: 메인 **"Brain"**, 재무 에이전트, 생각 기록 에이전트, 회고 에이전트.
- 다음 목표: **디스코드에 에이전트 채널**을 만들어 "어벤져스"처럼 여러 자아가 협업 → 존경하는 멘토들의 페르소나를 통합해 결정 자문·시야 확장.
- 궁극적 목표: **자식에게 물려줄 "나의 클론"**.

## 4. 실제 사례·수치

- **매일 새벽 2시** 자동 회고 실행(전체 라이프 데이터 입력).
- **ScreenPipe 30분 간격** AI 요약 → 상시 구동이므로 **로컬 모델** 사용.
- **목걸이형 웨어러블 24시간**, **화면 24시간** 녹화.
- **캡처 1건 → 노트 4~5개** 즉시 분할(ingest 후).
- **두 개의 볼트**(깊은 학습용 / 가벼운 참고용), **두 개의 폴더**(Raw / Wiki).
- 회고 주기 **5단**(일·주·월·분기·연): "10년간" 기획·회고 경력, 연말 **Life Accounting** 프로그램, 일기 기반 **3일 프로그램**.
- 2023년 말 아내를 만남 → 가명 **"홍길순"**으로 매달 일기 기록 → **GPT Turbo 시절** 모델로 기록을 연결해 러브스토리 생성 → **청혼서 작성에 실제 사용**. "기록 + AI가 어디까지 갈 수 있는지 알게 된 순간."
- 온톨로지 예시: Palantir 3요소(entity·relation·object), 커피 온톨로지 / 스타벅스 지식그래프, **BCG**·**Enterprise IQ** 노드 자동 연결.

## 5. 우리 볼트에 적용할 점

> 전제: 우리 볼트(`C:\Simbio`)는 이미 `AGENTS.md`(정본 지침) + `.agents/`(템플릿·스킬) + `_AI/_아린·_헤르메스·_클로드·_안티그래비티`(작업기록) 구조를 갖고 있다. 브라이언의 "**문서화가 곧 온톨로지**"라는 주장은 **우리 AGENTS.md가 이미 그 역할을 하고 있다**는 뜻이다 — 새로 만들 게 아니라, 이 문서를 온톨로지로 승격시키는 게 맞다.

- **① `Raw` / `Wiki` 2단 분리 도입 검토** — 지금은 캡처(인박스·`_인박스`)와 정리 노트가 섞여 있다. `원재료(자막·PDF·클립) → ingest → 개념 노트` 흐름을 폴더로 명시하면 ingest 스킬이 붙을 자리가 생긴다.

- **③ 상위 개념 노드(온톨로지) 등록** — `AX`, `Enterprise IQ`, `BCG`, `LLM Wiki`, `온톨로지 vs 지식그래프`처럼 여러 영상에 반복 등장하는 entity를 **고정 노트로 만들고 각 정리 노트에서 링크**한다. 다음 캡처가 자동으로 여기 붙는다.

- **⑤ 회고 자동화 후보** — 우리 볼트에 일일노트·작업기록이 이미 쌓이고 있다. 브라이언의 **"일간 → 주간 → 분기 → 연간" 5단 회고**와 **"데이터 출처를 함께 표시"** 규칙은 기존 크론(작업기록 집계)에 얹을 수 있는 현실적 다음 단계다. 단 "매일 새벽 2시 전량 입력"은 우리 볼트 규모·비용을 먼저 재봐야 한다.
