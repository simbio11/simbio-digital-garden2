> [!abstract] 핵심 요약 (Executive Summary)
> - LLM 위키는 "내가 고른 골드 재료를 채워둔 냉장고". 1부(브라이언)는 **raw → ingest → index → query**로 굴러가는 골드 데이터 파이프라인, 2부(김재경)는 그 위키를 **다중 에이전트 팀의 공유 워크스페이스**로 쓰는 운영법(agent.md·claude.md·soul.md·rules.md·훅 + 핸드오프·3단 검수 루프)이다. 결론은 하나 — 자동화는 되지만 **재료 선별과 사고는 사람 몫**이다.


## 1. 1부 — 위키의 본질 (골드 데이터, Gold In Gold Out)

**강사·전제**
- 브라이언: AI 연구소 재직(사업전략·교육 담당), 유튜브 채널 운영(자막 'Brain Trinity', 불확실), GIST AI 정책·전략 박사과정. 전날 찍은 강의 내용을 업데이트해 이날 공유.
- 2부는 김재경이 이어받아 1부에서 실시간으로 쌓은 지식을 AI로 쓰는 법을 시연. 두 사람이 서로 모르는 상태에서 같은 냉장고 비유를 써서 공동 세미나가 성사됨.

**도입 — "균열(The Fracture)"**
- LLM 기반 노트테이킹 유행 4~5개월. 그 사이 콘텐츠는 한 문장으로 수렴 — "**AI가 알아서 기억해준다**".
- 판정: **반은 맞고 반은 틀리다.** 이 말만 듣고 온 신규 옵시디언 사용자가 급증했지만 옵시디언은 2020년 소개된 6~7년 된 도구다. AI가 만든 내용을 **보기만 하는 용도**로 쓰는 것에 회의감 — "자동으로 기억된다" 뒤에 빠진 나머지(무엇으로 구성하고 어떻게 AI 활용으로 이어지는가)를 채우는 게 이 세션.

**LLM 위키의 정의**
- 위키의 핵심 = **누구나 편집할 수 있는 지식베이스**(위키피디아·나무위키처럼 아무나 '편집'을 누른다). 어원은 하와이어 'wiki wiki'(빨리빨리).
- LLM 위키 = 그 읽기·쓰기·편집 주체에 **LLM이 참여**하는 지식베이스.
- 최초 공개: **4월 2일 안드레이 카파시(Andrej Karpathy)**의 X 게시물(카파시 = OpenAI 공동창업, 전 테슬라 AI 총괄, 현 Eureka Labs).

**왜 필요한가 — 목적 2가지**
1. AI를 잘 쓰려면 좋은 데이터가 필요 → **좋은 데이터를 넣고 활용하고 재활용**하려고.
2. 데이터를 **AI가 늘 바로 꺼내 쓸 수 있게 정제**하려고.

**골드 데이터(Gold Data) 논리**
- AI는 "**시간이 동결된 뇌(frozen)**" — 학습 자체는 불가능하고 최신 정보는 검색으로 가져온다.
- 실제 문제 해결에 값진 것은 **내가 지금 필요한 최신 인터넷 데이터·보고서·AI가 모르는 것·내 경험·내 생각** = 골드 데이터. AI가 세상 지식을 다 알아도 **내 골드 데이터는 모른다**.
- 휴먼 문서 ≠ AI 문서: PDF·PPT·웹페이지는 사람용 포맷이라 AI가 읽을 때마다 **토큰이 낭비**된다 → **Markdown(.md)** 로 제공. `#` 헤딩·볼드로 섹션 구분과 중요도가 전달돼 AI가 가볍게 읽는다.
- 결론: **"Gold In, Gold Out"** — 골드(관련성·최신성) 데이터를 넣으면 품질 높은 결과가 나온다.

**냉장고 비유(두 사람이 독립적으로 같은 비유를 씀)**
- 사람 = 마트에서 재료를 고르는 장보기 담당. LLM 위키 = 재료를 **손질·소분해 언제든 꺼낼 수 있게 채워둔 냉장고**. AI = 재료를 꺼내 조리하는 **셰프**.
- 요약: **"AI가 기억하는 창고"가 아니라, 내가 고르고 느낀 골드 재료를 담아두고 AI가 요리에 맞게 꺼내 쓰는 냉장고.**
- 2부 확장 비유: 「냉장고를 부탁해」 팀 미션 / 「흑백요리사(Culinary Class Wars)」 — 여러 요리사(에이전트)가 공유 냉장고 재료를 바로 꺼내 쓴다("장보러 나갈" 필요 없음).

## 2. 원칙 셋과 RAG와의 차이

**RAG와의 차이(본인 표현 그대로)**
- RAG(Retrieval-Augmented Generation): 데이터를 **벡터화(숫자)** 해 저장 → 질문마다 필요한 것만 **검색·계산**해 상위(top) 결과만 사용. "계산으로 나오는 것을 쓰는" 방식.
- LLM 위키: **내 서재/책장을 직접 만드는 것** — AI가 전체 **목차(index)** 를 훑고 연결점을 따라 들어가 직접 찾아 쓰는 **사서(librarian)** 방식.
- 핵심 차이 = AI가 **전체 내용을 보고 스스로 판단**해 진행한다는 점.
- 발화 중 정정: "내 설명이 정확하진 않다"고 스스로 밝힘. **검색·계산으로 처리되는가 vs AI가 읽고 판단하는가**의 차이로 이해하라고 정리. 부작용: 개념 간 **연결은 AI가 결정**하므로 **입력 순서·모델·시점**에 따라 결과가 매번 달라진다.

**원칙 셋 (LLM 위키를 잘 쓰기 위한 전제)**
1. **나의 목적을 세운다** — 세상 지식을 다 긁어 먹이는 게 아니라, 무엇을 만들기 위해 어떤 지식을 쓸지(강의·프로젝트·스토리텔링·영상 편집 등) 정하고, 그 목표에 맞춰 **무엇을 모으고 무엇을 덜어낼지** 결정.
2. **내 기록·생각·판단이 반드시 들어간다** — AI가 정리해주더라도 사람의 개입이 필수. 개입이 없으면 그냥 위임한 것이고, 결과적으로 **골드 목표를 제대로 수집·선별하지 못한다**.
3. **AI 산출물과 사람 산출물을 분리**해 구축하고, 필요할 때 함께 쓸 수 있게 한다.

**파생 원칙 — "생각을 외주화하지 않는다"**
- 무엇을 질문할지, 어떻게 활용할지, 무엇을 만들지, 어떤 문제를 풀지는 사람이 정한다.
- "전부 자동화해야 하나 / 사람 손이 필요한가"라는 질문이 나오지만 **사람의 입력은 절대적으로 필수**. 다 맡기면 생각이 둔해진다.

## 3. 실제 명령·구조 (/ingest, /query, 파일명·폴더 구조)

**기본 골격 (원작자 기준 3폴더 + 보조 동작)**
- `raw` 폴더 — 사람이 읽는 날것의 원본(PDF 등)을 그대로 넣는 곳.
- **`ingest`**("소화하다") — 원본을 **MD 등 AI가 잘 읽는 형태로 정제**하고, 그 안에서 개념·인물·조직을 **분리 추출**해 위키로 만드는 단계. 글 A·글 B에서 각각 개념을 뽑아 **재사용 가능한 지식 조각**으로 정리.
- `index` — 추출한 지식을 연결해 만드는 **목차(내 서재의 전체 배치도)**. "무엇보다 index에 연결되는 것이 가장 중요하다."
- **`query`** — 목차를 먼저 읽고 → 관련 문서를 골라 → 연결점을 따라 들어가 **답과 출처(citation)를 제시**. 그 답으로 새 발견을 하고 새 콘텐츠를 만든다.
- **`lint`** — 깨진 링크, 고아 페이지(orphan), 끊긴 페이지, **중복**을 찾아 정리하는 **클리닝 스킬**(2부의 "주기적 cleanup script"와 같은 역할).
- 순환 구조: 새 지식 유입 → AI가 소화 → 소화된 것으로 **새 콘텐츠 생성** → 다시 유입.

**시연에서 실제로 한 일(브라이언)**
- 도구: **Obsidian** + **Obsidian Web Clipper**(자막 'LLM Obsidian Web Clipper')로 웹글 클리핑 → 폴더 `Clippings`(이름을 바꾸려다 유지). 클리핑이 일부 안 되면 **원문을 복사해 직접 붙여넣기**.
- 수집한 재료 2건 + **수집 이유까지 기록**:
  - ① OpenAI **"Harness Engineering"**(2월 11일 공유) — 인상 깊었던 문장 **"Human steers, agent executes"**(사람이 방향을 잡고 에이전트가 실행). 이 시점부터 'harness' 개념이 유명해짐.
  - ② **Tiago Forte**(세컨드 브레인 개념을 퍼뜨린 PKM 전문가)의 **"From Doer to Architect"**(8월 31일) — 실행자 → 설계자로의 이동, 사람과 AI의 역할 분리.
- **ingest 실행(Claude Code)**: "`Clippings 1` 폴더에서 최근 2개를 ingest" — 경로 단축키가 없어 **파일 경로를 직접 명시**하고 2건을 지목. 최신 수집분을 한꺼번에 처리시키면 **병목이 생기고 디테일을 놓친다**.
- ingest 중 실제 동작: 개념·용어 추출 → **"왜 수집했나요?"를 나에게 질문**(커스터마이즈한 부분. 인터넷 표준 스킬은 정리만 한다) → 답으로 **수집 맥락(context)을 붙여 저장**. 답 예: "사람과 에이전트의 역할 분리에 관심이 있어서 / 이걸로 영상을 만들고 싶다."
- 추출·연결된 개념: **harness engineering, funnel(불확실), context management, Tiago Forte** — 기존 개념(harness, workspace)과 **유사도·차이를 비교해 연결 추천**을 제시하고 **로컬 그래프(local graph)** 로 텍스트를 하나씩 연결.
- **query 실행**: **새 세션**에서 "위키 자료만 근거로 답하라"고 지시 → 질문 예 "사람과 에이전트의 협업 과정과 역할은 어떻게 분리되는가" → 위키 **index 전체를 읽고** 관련 문서를 선택 → 연결점을 따라가며 답변 + **출처 인용** → 이어서 "**이 내용을 종합(synthesis)해줘**"로 글·콘텐츠용 재료화.
- 유의: index가 너무 커지면 무거워진다(전체를 읽는 방식의 한계).

**확장(업그레이드) 연결 — 브라이언**
- **Zotero**(논문 읽기·필기 노트를 ingest로 연결), **DevonThink(DEVONthink, 맥 전용 저장소)**(거의 모든 소스 보관·AI 검색), **ScreenPipe**(화면 전체 녹화)·**Omi**(24시간 녹음) → 언제 무엇을 했고 무엇을 생각했는지 기록.
- 카카오톡·업무 메신저·이메일까지 전부 정리해 "나를 아는 데이터"로 만듦.
- **트레이드오프**: 장점 = 진짜 나를 아는 데이터 / 단점 = **관리 비용이 생각보다 큰 시간**을 잡아먹고, 최신 데이터를 계속 넣지 않으면 **옛 마인드셋 기준 답변**이 나온다.
- 확장 규모: 2부에서 "동료(재경)는 실제로 **약 155개 에이전트**를 운영 중"이라고 언급.

## 4. 2부 — 에이전트 팀 운영 (agent.md·claude.md·soul.md·rules.md·훅)

**왜 다중 에이전트인가 (3가지)**
1. 단일 세션은 **컨텍스트가 다 뒤섞여** 문제가 생긴다.
2. **관점이 하나**뿐이다 — 같은 모델이라도 **claude.md를 바꿔** 에이전트를 나누면 여러 관점으로 처리된다.
3. 단일 AI로는 **결과가 축적되지 않는다**(컨텍스트·작업 결과가 중앙화되지 않고, 한 AI에 다 물어보면 **무질서하게 커진다**).

**위키 = 다중 에이전트의 공유 워크스페이스**
- 팀 프로젝트의 **공유 문서 폴더**를 쓰는 이유와 같다 → **하나의 원본 데이터를 함께 본다**.
- 위키 안에 **에이전트별 별도 메인(작업) 폴더**를 두고, 각 폴더에 **memory, claude.md, soul.md, agent.md**를 분류해 둔다. 브라이언은 위키 **5개**(관리 번거로움), 김재경은 **1개**에 통합.
- `.claude`/`.agent` 같은 설정 폴더는 볼트에서 안 보이므로 `claude.md`·`soul.md` 같은 **별도 파일** + 공개용 **미러 문서**를 둔다.

**에이전트(=봇) 구성 실물**
- Discord에 봇으로 연결하고 **위키를 봇별 작업 공간으로 분할**.
- 예시 봇: **카파시**(전반 작업), **Doctor Strange**(일정), **Conan**(자료 정리), **손석희**(팩트체크·자료조사·Claude 총괄), **G-Dragon**(이미지 생성·편집), **페이커**(전반 작업), **글쓰는 재경**(글쓰기), **일론 머스크**(X 검색·팩트체크), **데미스 하사비스**(Gemini).
- 모델 배치(발화 기준): 손석희·G-Dragon = **Claude 3 Opus**(불확실), 카파시·페이커·글쓰는 재경 = **Claude**(버전 언급 없음), 하사비스 = **Gemini**(평은 안 좋지만 성능은 높게 평가).
- 다중 봇 vs 서브에이전트: **서브에이전트는 개별 육성이 어렵다.** 봇을 위키로 함께 키우면 **메모리를 따로 관리하기 쉽고**, 그 봇이 다시 **서브에이전트를 부릴 수 있다**.
- 잘 쓰는 사람은 봇을 안 나눠도 **프로젝트 폴더와 에이전트를 따로 설정**한다.

**파일 구조 — 역할 분담(핵심)**
- **최상위 `agent.md` = 헌법(constitution)**: **가드레일(guardrails) · 완료 게이트(completion gates) · 핵심 경로 포인터(core path pointers)**.
- **`claude.md` / `agent.md`(봇별)** = 각 봇의 **정체성·역할 설정 문서**. 예: Conan은 claude.md에 **리서치·자료 수집 담당**, 그리고 **데이터를 어떻게 저장할지에 대한 원칙**까지 들어 있다.
- **`soul.md` = 말투(tone of voice) 문서** + 프로필 이미지. 재미가 아니라 **여러 봇을 돌릴 때 누가 뭘 하는지 잃지 않기 위한 장치**. 예: Conan은 "코난 에도가와입니다", "진실은 언제나 하나" 같은 대사가 응답에 붙는다. 봇마다 프로필을 주면 **실제 팀원과 일하는 감각**이 나 구분이 잘 된다. 부작용: 세션이 길어지면 **말투가 안 나오고 엉킨다**.
- **`rules.md` = 상황별 라우팅 문서**: 길어서 **매번 다 읽게 하지 않는다** → 상황별로 해당 규칙만 읽게 라우팅. 규칙 묶음: **Discord 관련 / 도구 관련 / 한국어 응답 지침 / (재경) 글쓰기 스타일 지침**.
  - 첫 규칙 예: **"사용자는 터미널 스크립트를 읽지 않는다"** → Discord로만 응답, **파일이 3개를 넘으면 압축 전송**.
  - 메모리 규칙: **공유 메모리 규칙**, 대화 시작 방법, **세션 시작 훅**, 작업 디렉터리 **memory index**. 개별·공유 메모리를 분리하고 **훅이 자동 주입**, 공유 범위는 **인덱스에 등록된 것만**.
  - 한계: 다 정독한 게 아니라 **AI가 자동 추가한 규칙도 많다**.

**훅(hooks)**
- 구성: **MD 파일에 들어가는 규칙** + **훅·Python 코드로 강제되는 규칙**이 맞물려 작업 수행.
- **Claude Code가 Codex보다 훅 종류가 훨씬 많다**(체감 1.5배 이상, 정확한 수 비교는 안 함, 불확실).
- 사용 예: **컨텍스트 압축(compression) 후 트리거**, **압축 전 특정 상황 저장**, **압축 후 특정 문서 강제 읽기**.
- 부작용: 훅이 많아지면 **AI가 무거워진다** → 최근 '**harness(하네스) 비우기**'가 화제. **한 번에 다 지우지 말고 하나씩 다시 추가** 중. ("조금씩 비우는 게 나은 전략.")

**봇별 메모리 운용**
- 마스터 봇: **과거 실수를 문장으로 많이 포함**. 작업 봇: **어떻게 잘못됐는지** 기록.
- 검증 봇: **Claude 3 Opus**(불확실) — Opus가 **말을 너무 많이 정정·철회하는 경향**이 있어 메모리로 관리 방법을 지시.
- **결정할 게 없으면 Discord로 보내지 말고 봇끼리 먼저 논의**하게 한다.
- 작업 로그: **SQLite 데이터베이스**로 현재 작업을 모니터링하고 함께 리뷰.
- 봇끼리 서로를 **주기적으로 평가**. 예: 팩트체크는 높고 글쓰기는 낮은 점수 → **Opus 3.5**(불확실)로 같은 평가를 시켜도 **완전히 다른 평가**. 같은 작업도 **설정에 따라 판단이 갈려** 봇을 나누는 게 낫다.

## 5. 핸드오프·검수 루프

**위키 ↔ 봇 연결(검색·산출물)**
- 제공 문서: ① **폴더 구조표**(코드로 작성해 AI가 구조를 즉시 보게 함) ② **별도 목차(TOC) 문서**(더 넓게 묶어 TOC 따라 드릴다운) — 예: Fast Campus → 녹화 강의·세미나 문서, 어떤 매니저와 일했는지까지 연결. 목적은 **AI가 작업할 때 원래 맥락을 잃지 않게** 하는 것.
- **새 노트 규칙**: 기존 노트로 **최소 3개의 링크**를 포함. 잘 안 지켜지므로 **주기적 cleanup script 실행**(1부 lint와 같은 역할).
- 회의 기록 4종: ① **컨텍스트 문서** ② **순서(order) 문서** ③ **실시간 회의록(meeting) 문서** ④ **아웃컴(outcome) 문서** — 완료를 알려주면 'finished'로 채워진다. 회의 과정부터 최종 완료 문서까지 남겨 **나중에 에이전트 수리(repair)에 재활용**(로그는 사람이 읽기 어렵고, 실제 산출물에 연결된 문서가 있으면 AI가 맥락을 더 잘 이해한다).
- Discord에서도 회의: 채널 2개(브라이언 자료로 **슬라이드 제작** / **PDF 제작**), 봇들이 **서로 태그**하며 회의하고 결과를 공유.

**1부 지식의 재료화(10분 브레이크에 실제로 한 일)**
- 회의록(semi-automated skill): 종료 시각이 매번 달라 반자동. Trello 회의록에 5건 추가(많이 가져오라고 시킴).
- 1부 발표가 **Markdown 문서**로 저장되고 개념 문서도 자동 생성 — 골드 데이터, RAG 검색 방식 차이, 지시·query 원칙, 확장성, 관리 비용이 반영되고 **기존 문서와 연결**.
- 저장 위치 예: `Requests` 폴더 → **Fast Campus** → **Trello 회의록** 섹션.
- 원칙: "**garbage in → gold in → gold out**". 봇이 쓰레기를 냉장고에 넣게 두면 기계적이 되므로 **human-in-the-loop**가 중요.

**핸드오프 구조**
- 봇 지휘(오케스트레이션)는 주로 **카파시(자막 'Kappa-C', 불확실)** 에게, 작업이 많으면 **페이커**에게도 위임.
- 슬라이드 제작: **카파시에게 핸드오프 → 카파시가 제작을 오케스트레이션 → 봇 3개로 3단계 검수 루프 → 최종 전달**. 카파시는 작업을 나눠 **무엇을 서브에이전트에, 무엇을 다른 봇에** 줄지 결정하고, 재경은 **보고를 받으며 회의록을 갱신**하고 **위키 검색 1회**.
- 프롬프트 다듬기: **Ouroboros 플러그인**(이재교 님 제작, 해커톤 수상자·패스트캠퍼스 강의)으로 **소크라테스식 문답**을 하며 모호한 질문을 완성된 질문으로 바꾸고, 그 결과를 **위키에 저장해 나중에 참조**.

**검수 루프(역할별 분담 — 실제 파이프라인)**
- 슬라이드: **글쓰는 재경 봇** = 표기·말투·은어 점검 / **Gemini 봇** = 이미지 깨짐·오삽입·크기 검증 / **손석희 봇** = **적대적 리뷰(adversarial review)** — "Claude 코드를 온전히 믿을 수 없다"는 전제로 슬라이드 필요성·논리 흐름 점검.
- PDF: 지인(자막 '공양님', 불확실) 스킬을 다듬어 **Word 초안 → 최종 PDF** 변환. **검증 게이트는 Python 코드로 엄격하게**. 슬라이드와 거의 동일하게 **표기·비주얼·내용 구성**을 논의한 뒤 생산.
- 결과물: 브라이언 제공 자료 + 세미나 기획 문서만으로 **PDF 책 형태**까지 제작, 완성도 높음.
- **검수 원칙(중요)**: "**리뷰어는 만든 사람이 아니어야 하고, 원자료로부터 독립적이어야 한다.**" 실제로 만든 사람이 아닌 리뷰어가 슬라이드에서 **중대 이슈 2건**을 적발.
- 검수 흔적은 산출물에 그대로 남는다 — "이 문장이 어색하다", "이 표 번호가 맞지 않다".

**자동화의 한계(재경 본인 정리)**
- 슬라이드 제작 자동화 범위는 **최대 60%**. 기존 자료가 많아도 **매번 상황이 다르고 하고 싶은 말이 달라서** 핵심 내용은 **수동 입력이 더 깔끔**.
- 대신 **슬라이드 스크린샷 삽입은 자동** — AI가 "무엇을 캡처하는지, 그 맥락"을 안다. 조합: **Make/Zapier** 연동, 슬라이드는 **Claude Designs(불확실)** 제작 후 **Make로 원격 제어**.
- 최종 시연: Discord에서 말하면 **터미널로 들어가 쉬는 봇에게 작업 전달**(예: "세미나 참석자들에게 친절한 인사") → 봇이 응답. 안내: Agent Korea 카톡방(공동 관리자)·디스코드의 **'Fable-Kappa' Q&A 룸**(자막 'Fable'·'Kappa', 불확실)에서 봇에게 세미나 내용 질문 가능.

## 6. 우리 볼트에 적용할 점

- **폴더 골격 + index**: `raw`(사람용 원본)/수집함/wiki(정제)/index(목차)로 분리하고, 폴더 구조표(코드 형태)+사람이 읽는 목차 문서를 두어 봇이 작업 전에 먼저 읽게 한다.
- **ingest 스킬 자체 제작**: "왜 수집했는지"를 **반드시 되묻게** 만들고 맥락을 노트에 붙여 저장(표준 스킬은 정리만 한다). 대상은 **경로를 명시해 2~3건씩** — 한 번에 돌리면 병목·누락.
- **규칙은 라우팅으로**: 우리 규칙/에이전트 설정을 **상황별 문서**(Discord·도구·한국어 응답·말투)로 쪼개고 전부 매번 읽히지 않는다.
- **검수 루프 명문화**: "리뷰어는 만든 봇이 아니고 원자료에서 독립적"을 봇·크론 규칙에 넣고, 회의록에 **컨텍스트·순서·회의록·아웃컴 4문서** 패턴을 도입(사후 복구·수리가 쉬워진다).
- **3링크 규칙 + 주기 lint**: 3링크 규칙은 안 지켜지므로 **lint를 주기 크론**으로(깨진 링크·고아 노트·중복).
- **자동화는 60% 선**(핵심 메시지는 사람이 직접, 반복 노동만 자동화). **적용 순서**: ① raw+ingest 스킬 → ② index 문서 → ③ 봇별 폴더·메모리 → ④ 규칙 라우팅·훅 → ⑤ 검수 루프·lint 크론.

## 7. 주의·한계

- **자동 생성 영어 자막(한국어 영상의 영어 자동번역)을 한국어로 옮긴 것**이라 고유명사·전문용어 오역 위험이 크다. 자막에서 **LLM 위키가 'LRMK·LM Wiki·LM Key·AL Key'**, 카파시가 **'Kappa'** 등으로 뒤섞여 표기된다(오인식, 불확실).
- **화면으로 보여준 것을 자막만으로 확인할 수 없어** 들리는 표기를 그대로 적었다. `agent.md`·`claude.md`·`soul.md`·`rules.md`·`memory`·`index`(TOC)·`.claude`/`.agent`·`raw`/`Clippings`/`Requests`는 언급이 명확하나, **모델 버전(Claude 3 Opus, Opus 3.5, Opus 5, Astra, Fable)과 플러그인·인물명(카파시/Kappa-C, Claude Designs, 공양님, 구원 교수, Brain Trinity)은 불확실**.
- **명령어 전체 문자열은 확인 불가.** `/ingest`·`/query`·`lint`는 **개념·스킬 이름으로 언급**된 것이며 실제 호출 문법은 공개되지 않았다. 구체 자료는 **세미나 참가자에게 제공**된다고만 언급.
- **관리 비용**이 크다 — 최신 데이터를 계속 넣지 않으면 옛 정보 기반 답변이 나오고, 봇·훅·규칙을 늘리면 무거워진다(두 강사 모두 "정리를 조금씩, 급하면 오히려 더 나쁘다").
- **연결의 비결정성**: 개념 연결은 AI가 결정하므로 **입력 순서·모델·시점에 따라 결과가 매번 달라진다**. 재현이 안 된다는 전제로 운영해야 한다.
- **사람 손을 빼는 자동화는 이 영상의 결론과 반대다.** "생각의 외주화"는 명시적으로 경고되며, 목적 설정·선별·질문 설계가 전제다.
- 2부는 **시간 부족으로 시연이 일부 꼬였다** — 컴퓨터가 느려지고 정체불명의 박스가 뜨고 HTML이 안 열렸고 슬라이드가 아닌 다른 문서가 생성되는 등 **오류가 실제로 발생**했다. 일부는 **강사가 스스로 정정**했고(RAG 설명 정확도, 시연 순서 등), 애매한 대목은 발화 그대로 남겼다.
